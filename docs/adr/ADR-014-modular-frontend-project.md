# ADR-014 前端源码、组件与确定性构建

状态：accepted。日期：2026-10-24。负责人：Cano。审批：agent_delegated，human_reviewed=false。[TASK-047](../tasks/TASK-047-frontend-project-and-component-system.md)。

## 背景

用户要求网页成为可开发、可复用、可回退与重新进入的规范项目，明确不加入面包屑。既有hash子页面已具备状态恢复，但HTML/JS/CSS集中大文件，公共分页/控件依赖散在样式，后续修改容易相互影响。现有服务及安装包通过固定白名单提供根级三个静态资产，业务与科学证据必须保持。

## 决定

开发入口改为web/src、web/styles、routes.json与frontend.json。主壳和9个页面/教学片段独立维护；页面控制器、共享科学事实、启动/状态/路由按职责拆分。PageRegistry提供register/load生命周期，router负责URL/history与恢复。新增页面可由脚手架创建并登记。

FlavoUI闭包封装DOM、按钮、表单、标签、键值、分页、列表条目、状态/空态、面板和分栏API，并有类型契约及独立组件参考页。现有业务实际复用这些API，静态/新增DOM通过mount使用相同UI类。组件不发起API请求。公共token和明确的reader/compare/diagram/explore布局模板约束页面，不把科学语义差异强行合并。

纯Python标准库构建器按显式清单组装三份运行资产并同步包镜像；check拒绝产物漂移、DOM ID重复、路由/模板失配、include循环及越界路径。check接入工程CI。运行服务保持原三个文件，无新静态路由、前端运行依赖或服务重启。开发增加构建/监听步骤，替代历史规划中的“无构建步骤”约束。

JS采用有明确依赖顺序的经典脚本构建片段，不声称已迁为原生ES模块。现有业务全局名称及启动顺序保留；公共UI闭包、PageRegistry与新增页面闭包提供清晰扩展边界。生成文件不手工编辑。

## 备选方案

- 只增加规范文档：仍会复制控件和修改大文件，无法保证实际调用和产物一致。
- 直接引入React/Vue及新的包构建工具：可进一步隔离状态，但当前会同时改动渲染、路由、部署和大批业务交互，成本与回归风险更高。
- 原生ES模块直接服务：需要调整现有静态路径白名单/安装包和运行中服务，当前无必要。

选择保持运行合同、将开发源和组件分离的渐进方案，满足当前可操作开发流程。

## 影响与风险

源码变更需build，CI check防止漏构建。公共样式有统一权威入口，原领域页面样式保留必要的层叠顺序。既有业务仍共享经典脚本作用域，清单顺序属于兼容合同；新私有状态放页面闭包，跨页通过路由/公共组件交互，不继续扩大隐式耦合。

组件示例与工程检查不产生化学证据，来源/库存/搜索/原始运行身份不变。教学原顶部间距与背景遮挡、既有练习schema及旧run链接保持。无面包屑。

## 复审条件

若出现无法通过清单和页面生命周期隔离的依赖、需要独立代码加载或服务端渲染，再以新TASK评估原生模块或框架。保持现有分享URL、包资产与科学证据边界兼容。
